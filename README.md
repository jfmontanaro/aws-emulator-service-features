# AWS Emulator with experimental per-service Cargo features

Emulating AWS services is great, but AWS has a lot of services (citation needed). Most apps interact with only a few of them. But `aws/aws-emulator` is currently all or nothing. You either emulate everything, or you emulate nothing. This means that, for instance, a release build of the binary weighs in at nearly 1GB, and consumes ~160MB of memory just sitting there idle doing nothing. In embedded mode it's even worse: Compiling your tests that depend on `aws-emulator` requires compiling all 400+ service crates, which can take quite a while and consume tens of GB on disk in the `target/` directory.

However, if we split all of the service-specific crates out into their own Cargo features, we can get away with compiling a lot let code.

To be specific: A test project comiled against this fork of `aws-emulator` with only the `s3` features active compiles tests in under 3 minutes on my machine, and consumes about 12GB of disk space. A release build of the standalone server with only `s3` active compiles in about 5 minutes, produces a 115MB binary, starts up in ~35ms, and consumes about 33MB idle memory. That's low enough that it would be feasible to, for instance, spin up a separate `aws-emulator` process for each test that wants one, rather than trying to share a single process across many tests.

This shouldn't be thought of as a final design - in particular it requires modifying the router's `lib.rs` and `Cargo.toml`, both of which are auto-generated files, so the generator would need to be updated. Obviously, some thought would need to be given to testing each of the per-service features in isolation as well. But I think this shows that the idea has legs, and should be considered, because right now embedded-mode absolutely sucks to use in practice.
